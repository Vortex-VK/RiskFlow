# Retained transaction analysis (V2 historical profiling)

RiskFlow now offers two explicit workflows. **Import CSV** creates a temporary editable sandbox, as before. **Datasets** opens retained history. Starting or refreshing the application still opens an empty sandbox; a saved dataset is never selected automatically.

## Using a dataset

1. Open **Datasets**, enter a name and a stable source namespace, and create the dataset. Use one namespace for exports with the same account/transaction identity system. Each dataset has one namespace in this phase.
2. Upload a CSV inside that dataset and select **Preview retained import**. Columns & format starts collapsed. The backend resolves the mapping and reports every row as added, duplicate, conflicting or invalid. Unsupported analytical activity is shown separately from import validity.
3. Select **Commit records**. Invalid rows, unresolved identity conflicts, or a complete-history capacity violation prevent the entire import from committing. For changed events, **Review changed records** shows normalized previous/proposed values. Select corrections, enter a reason and use **Preview selected corrections** before committing the new preview. Previewing never changes accepted history. Repeating a successful commit or importing overlapping records does not duplicate transactions.
4. Select **Assess retained history**. This computes the complete accepted revision, independently of graph navigation and playback. Inspect coverage, source IDs and investigation recommendations, or replay supported purchases using the existing graph.
5. **Saved assessments** reopens frozen results, including results from earlier revisions. **Retained activity** pages through current source records, including types not yet analyzed. Expand a record and select **Show record versions** to inspect earlier values, source availability, local recording time and correction reasons.
6. **Create editable sandbox copy** explicitly copies the supported purchase projection. Edits affect only that sandbox. They do not correct stored source records or rewrite earlier runs.

## What the results mean

- **No alert**, **review**, and **high priority** map the existing thresholds to investigation language. They do not authorize, decline or reverse real payments.
- Rule points are not calibrated fraud probabilities. A high score is not confirmed fraud, and no alert does not establish safety.
- **Complete** means all six current rules could be evaluated; it does not mean all relevant fraud signals exist. **Partial** reports how many were evaluated. **Not assessed** has a null score, including when every signal is unavailable.
- Each evaluated purchase retains its measurements, threshold settings, explanations and profile evidence. Missing baselines do not become normal behavior. Source availability and local retention time are distinct fields.
- Current scoring still covers USD outgoing purchase/payment/charge/bill-payment and explicit authorization attempts in supported statuses. Pending, declined and failed attempts participate in attempt windows. Explicit captures, refunds, reversals and status updates do not create additional scored attempts.
- Transfers, withdrawals, refunds, unknown types/statuses/directions, and other currencies remain visible without invented purchase scores. Purchase accounting and linked refunds/reversals are separate from scoring. Separate reference-profile files are not loaded automatically.
- Device observation is not proof of legitimate ownership. Saved assessments now use historical familiarity and explicit trust/revocation assertions. The temporary V1 sandbox remains unchanged. See [historical profiles](historical-profiles.md) for populations, evidence, configuration and validation limits.

## Identity, chronology and reproducibility

Transaction identity is the exact source namespace + account ID + source event ID. Case is preserved. Missing IDs are invalid; matching amount/time alone never merges two purchases. Existing alias priority is preserved so reimports do not silently change identity. When both `event_id` and `transaction_id` exist, explicitly map **source event id** to the unique lifecycle event column; the legacy default selects `transaction_id`. Each authorization, partial capture or adjustment needs its own stable event ID. A shared transaction/intent ID belongs in `underlying_transaction_id`.

Changed normalized content under an existing identity is a conflict, including changed additional source context. Corrections require explicit selection and a reason, then a new preview and commit. They insert a new version at a new retained revision; previous payloads, hashes, imports and runs remain intact. Declared correction availability must be later than the previous version's declared availability. Missing availability permits retrospective corrections but prevents source-as-known reconstruction. Reimporting a superseded payload becomes a conflict, not an automatic rollback. Identity changes are new records, not correction-based account merging.

Canonical event/entity IDs use SHA-256 prefixes with kind prefixes. V2 timestamp ties are ordered by canonical event ID, independently of file order or batch packaging. Original V1 IDs and tie ordering are untouched. Merchant IDs take precedence over merchant labels; a label/country fallback supports the existing display projection but does not prove a legal counterparty or an account-to-account relationship. Missing context placeholders exist only in the V1 projection and have the affected rules disabled.

New runs use adapter `retained-v2`, taxonomy `categories-v1`, envelope `assessment-v2.4`, accounting `lifecycle-v1`, profiles `profiles-v2`, engine `engine-v3` and the unchanged point schedule `rules-v1`. Historical profiles supply per-event baselines; static V1 simulations retain `engine-v1`. The [merchant amount range](merchant-amount-range.md) suppresses only amount points when qualifying earlier spending covers the current amount, with inspectable records, dates and maximum. Select **Assess retained history** to create a result with this version. Saved `assessment-v2.1`, `assessment-v2.2` and `assessment-v2.3` runs remain readable without recomputation or changes to their scores. Import records retain original bytes, mapping/options and preview. Pending previews created under the previous importer must be recreated; successful historical commits remain idempotent. Existing records are not silently renormalized when aliases change.

The input hash covers canonical facts and additional context, excluding raw formatting, file grouping and local import timestamps. The analysis hash adds calculation/configuration versions and policy/cost settings. Equivalent accepted facts produce equivalent scores and analytical hashes even when dataset UUID, revision numbers or import partitions differ. Stored content hashes are checked before calculation. Playback position and graph layout do not enter those hashes.

Runs default to **retrospective**, selecting the latest accepted event versions at the selected retained revision. Under **Historical availability**, select a UTC cutoff to reconstruct an **as-known source snapshot**. Every retained version within that revision must have a precise event time and `source_available_at`; availability must not precede event time. The latest version available by the cutoff is selected, including the original version if a correction became available later. Unknown timing rejects this mode instead of inventing provenance. Records available exactly at the cutoff are included.

This is a single-cutoff source snapshot, bounded by what has been retained in that revision. It is not the local database's historical state and not a per-transaction authorization backtest: calculations analyze the selected snapshot in event-time order. A later source record with genuinely earlier declared availability can change a newly reconstructed snapshot; the earlier saved run remains immutable. Source timestamps are assertions, not independently verified provenance. No original-authorization effectiveness claim is supported. Arbitrary event-time ranges, per-field effective histories, and per-decision operational replay remain unimplemented. Mode, cutoff and accounting version are included in the analysis hash.

## Lifecycle fields and accounting

`lifecycle_kind` accepts `authorization`, `capture`, `refund`, `reversal`, `status_update` and `unspecified` (the default). Matching explicit activity types can also identify lifecycle kinds. Ordinary purchase/payment/charge/bill-payment records without lifecycle metadata keep legacy standalone behavior: one attempt and, when completed, one settled purchase. Multiple purchase/authorization/capture records sharing an underlying transaction ID need explicit roles; ambiguous legacy purchase rows are unresolved rather than counted again.

`related_event_id` references a source event ID in the same source namespace and account. It is never a merchant ID, graph object ID or an amount/time match. If supplied, underlying transaction IDs must agree. Currency must agree and the target cannot occur later than the related event. Links missing from the selected snapshot remain unresolved.

- Authorizations count as attempts, including declines. Even a completed authorization is not a capture.
- Completed outgoing captures contribute settled spending. Several distinct partial captures are additive. A capture may link to a successful/pending authorization; a standalone completed capture still establishes spending even when its authorization is absent. Broken declared links remain visible as unresolved; their independently known capture amount is included in recognized spending.
- Completed incoming refunds and capture reversals reduce recognized net outflow only when linked to a recognized settled purchase/capture. Aggregate adjustments cannot exceed the target's remaining amount. Excess or ambiguous adjustments stay unresolved; no negative residual or inferred FX is introduced.
- A completed reversal linked to an authorization is a release, not a refund of settled spending. It does not reduce captured amounts; reverse the specific capture to represent that movement.
- Status updates are observations, not additional attempts or money movements. A status update alone does not transform a pending capture into settled spending; supply an explicit capture event or a reviewed correction of the capture's status. Update-to-update links remain unresolved.

Totals are grouped by currency and use the source amounts at the importer's fixed hundredths precision. There is no currency conversion, currency-specific exponent normalization, account-balance reconstruction, or general ledger. Unresolved/excluded counts are shown with totals; recognized net outflow is not a complete account balance. Salary, transfers and withdrawals remain outside purchase accounting. Linkage resolution is not risk-rule availability or evidence of legitimacy. Equal-time adjustments use canonical ID order, consistently across import packaging.

The synthetic [lifecycle example](../fixtures/evaluations/simulator-v2/lifecycle.csv) has two attempts, USD 100 settled through two partial captures, USD 20 refunded and USD 40 reversed: USD 40 recognized net outflow. Its status update and authorization release add no spending. This is an accounting fixture, not fraud ground truth.

## Formats and limits

Saved imports accept UTF-8/BOM and BOM-marked UTF-16, comma/semicolon/tab delimiters and Excel `sep=` directives. Quoted fields, CRLF and multiline values are handled by Python's CSV reader. Explicit column overrides, decimal separators, ISO/month-first/day-first dates and UTC offsets are available. Amounts use exact minor units, including grouped monetary formats. Sub-millisecond times are rejected instead of silently truncated. Naive instants require an explicit offset; date-only records are retained with declared date precision and disable intraday windows in the complete eligible projection.

Source event ID, account ID, time, amount and currency are required for retention. This is deliberately stricter than the temporary sandbox importer, which can create presentation IDs or defaults. Type/status are not guessed when absent. Separate debit/credit columns can supply the amount and explicit direction when no amount is present; negative values or two nonzero sides are rejected. Separate date/time columns can supply the timestamp. Supported timestamps remain 1900–2100; amounts have at most two decimal places and absolute value at most 100,000,000 minor units. Other absent direction values remain unknown; the sandbox's convenience defaults are unchanged.

Limits are 5 MiB per source CSV, 20,000 rows per import, and 20,000 accepted source events per dataset. The full eligible projection must also fit 10,000 payments, 1,000 objects and 20,000 associations. A preview reports overflow and preserves prior accepted state. No history is sampled, truncated or evicted to fit the canvas. Activity lists are paginated; evidence displays preserve the existing 50-ID display cap and full counts. Complete accepted source records remain accessible at the run's revision through the activity API.

## Local storage and recovery

By default, the backend stores history in repository `.data/riskflow.sqlite3`. Set `RISKFLOW_DATA_DIR` before launching the backend to select a different directory. This is separate from browser/session state. Initialization is lazy, so legacy V1-only use does not create a history database. The runtime directory is ignored by version control.

The database retains original uploaded bytes, import previews (including rejected/conflicting candidates), every accepted source version, correction reasons and frozen run outputs. There is no automatic expiry or dataset deletion. For a consistent simple backup, stop the backend and copy the database file; restore it while the backend is stopped. Migration 2 atomically upgrades Phase 1 storage to append-only event versions and preview-version metadata, preserving existing payloads/hashes and saved runs. Concurrent initializations are serialized. An unknown newer schema version is rejected without replacement. Older application builds cannot open the upgraded schema; restore a pre-upgrade backup if reverting application versions. Legacy sandbox snapshots are not silently converted into source history.

This remains a local application; V2 does not add authentication, shared-user tenancy, public hosting or financial-service integration. Browser and backend tests inject temporary storage and never use the user's history database.

## Verification and effectiveness boundary

The supplied 2,400-row synthetic file retains all rows: 1,953 eligible attempts and 447 unassessed activities. Eligible calculations preserve the V1 1,933 approve / 16 review / 4 block outcomes, presented in V2 as investigation recommendations. Independent direct-scan tests check five-minute windows. The shared-device burst produces 20,20,45,45,70,70,80,80 across full, split, overlapping and restarted imports. Negative tests cover changed content, missing identity, duplicate commits, stale previews, malformed money, absent timezones, future events, projection overflow, transaction rollback and cross-dataset access.

These establish reproducibility and data-handling behavior. They do not establish useful fraud detection. Confirmed outcomes, representative chronological backtesting, false-positive workload, recall, precision and detection-delay evaluation remain necessary before a trustworthiness claim about real-world monitoring.

Purchases and merchant-specific bills have distinct sample/span/freshness requirements; missing evidence stays unavailable.
